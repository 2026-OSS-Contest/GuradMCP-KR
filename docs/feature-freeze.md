# 기능 동결 런북 (GMCP-43)

W7(2026-08-20) 기능 동결 이벤트를 실행하기 위한 판정 기준과 당일 체크리스트입니다. 이 문서는 동결 "당일에 무엇을 확인하고 무엇을 하는가"에 집중한 실행 문서이며, 우선순위 근거(FR 전체의 M/S/N 분류)는 Plane GMCP-4 "MVP/Stretch Scope 문서화" 이슈의 산출물을 기준으로 합니다.

## 1. 동결 원칙

기능 동결은 "더 이상 새로운 기능을 늘리지 않고, 있는 기능을 제출 가능한 상태로 다듬는다"는 원칙입니다.

**허용되는 변경**

- 버그 수정 (`fix`)
- 문서 보강·번역 (`docs`)
- 시연 준비: 데모 시드 데이터, 데모 스크립트, `docker compose --profile demo` 안정화
- 테스트 보강 (`test`), CI 안정화 (`ci`)
- 위 변경에 수반되는 최소한의 리팩터링

**금지되는 변경**

- 신규 정책 action, 신규 탐지기, 신규 API 엔드포인트 등 새 기능(`feat`)
- Should 이하 항목 중 동결 시점에 미완료로 판정된 기능의 재개
- 데이터 모델·정책 DSL의 하위 호환을 깨는 변경(`!` breaking change)
- 스코프 확장을 유발하는 의존성 추가

동결 이후 `feat` 커밋이 필요하다고 판단되면 반드시 3장의 예외 승인 절차를 거칩니다.

## 2. 동결 판정 기준

GMCP-4 문서의 FR 표는 각 기능 요구사항(FR)을 Must(M) / Should(S) / Could 또는 Stretch(N)로 분류합니다. 동결일에는 이 표를 기준으로 다음 절차를 따릅니다.

| 우선순위 | 판정 절차 |
| --- | --- |
| **Must** | 완료 확인만 합니다. 미완료 Must 항목이 있으면 동결을 선언하지 않고, 팀 합의로 완료 시점을 재조정하거나 해당 항목을 Should로 재분류합니다(합의 기록 필수, 3장 참조). |
| **Should** | 동결 시점 완료 여부로 "동결"과 "이월" 중 하나로 판정합니다. 완료된 Should는 그대로 유지, 미완료 Should는 아래 기준으로 나눕니다. |
| **Could / Stretch(N)** | 원칙적으로 전량 동결(=이번 제출 범위 제외) 대상입니다. 예외적으로 진행 중이며 반나절 이내 완료 가능한 항목만 예외 승인 절차로 유지할 수 있습니다. |

Should 이하 미완료 항목의 동결/이월 판정 기준:

- **동결(carry-drop)**: 제출 마감(2026-08-27)까지 완료가 시연·평가에 필요하지 않고, 미완료 상태로도 데모가 정상 동작한다 → 이번 범위에서 제외, 차기 이슈로만 기록.
- **이월(carry-forward)**: 제출 마감까지는 필요 없지만 M3 이후 로드맵에 포함되어야 한다 → Plane 백로그에 유지하고 마일스톤만 해제.
- 두 판정 모두 **팀 합의**가 있어야 확정됩니다. 담당자 단독 판단으로 동결/이월을 정하지 않습니다.

## 3. 동결 실행 체크리스트 (8/20 당일)

### 3.1 브랜치 정책

- [ ] `dev` 기준 열려 있는 모든 feature PR을 검토해 병합 또는 종료(close) 처리
- [ ] 동결 시점 이후 새 `feature/*` 브랜치 생성 금지(리뷰어는 신규 feature PR을 동결 예외 승인 없이는 병합하지 않음)
- [ ] `fix/*`, `docs/*` 브랜치는 계속 허용
- [ ] `main`/`dev` 브랜치 보호 규칙 재확인(강제 push 금지 유지)

### 3.2 라벨/상태 처리 (Plane)

- [ ] Must 항목 전체를 `Done` 상태로 확인
- [ ] 동결 판정된 Should 이하 항목을 Plane **`Frozen`** 상태로 전환(설명: "기능 동결 이후 변경 금지")
- [ ] 이월 판정된 항목은 상태를 `Backlog`로 되돌리고 현재 마일스톤에서 제거, 다음 마일스톤 라벨만 남김
- [ ] 동결 목록과 이월 목록을 GMCP-43 코멘트에 표로 정리해 남김(항목 ID, 판정, 사유)

### 3.3 예외 승인 절차 (팀 합의 기록)

동결 이후에도 신규 기능이 필요하다고 판단되는 경우에만 사용합니다.

1. 예외 요청자가 GMCP-43(또는 해당 FR 이슈)에 코멘트로 요청 사유·예상 작업량·영향 범위를 남긴다.
2. 최소 1인 이상의 다른 기여자가 코멘트로 동의를 남긴다(비동기 합의 가능, 대면/음성 합의 시에도 결과는 반드시 코멘트로 기록).
3. 승인된 예외는 해당 이슈에 `frozen-exception` 라벨을 부여하고 상태를 `Ready`로 되돌린 뒤 작업한다.
4. 예외 작업의 PR 설명에 승인 코멘트 링크를 포함한다.

합의 기록이 없는 `feat` 커밋은 리뷰에서 반려합니다.

## 4. 동결 이후 릴리스 절차와의 연결

기능 동결이 끝나면 남은 작업은 버그 수정·문서·시연 준비뿐이므로, 이 시점부터 [최종 제출 패키징 체크리스트](submission-checklist.md)(GMCP-48)를 병행 진행합니다.

- 동결 직후: `docs/submission-checklist.md`의 제출물 목록을 기준으로 담당자 배정
- 버그 수정이 안정화되는 시점: `v1.0.0` 태깅 절차 착수(제출물 목록의 태깅·패키징 절차 참고)
- 제출 마감(2026-08-27) 전: 제출 체크리스트의 최종 검증 커맨드를 실행해 릴리스 후보를 확정
